# 03 — The ABC Combo Matrix (methods × environments)

## Full-dark field intelligence (verified on the ground)

These three facts come from surviving a real full-dark period — they are the reason
"combination" is the core design principle, and they are now encoded in the planner
(`algo.rs::env_fit`) and auto-generated per profile:

1. **VLESS + Psiphon worked when BOTH were closed alone.** Chaining them (VLESS inside
   the Psiphon tunnel) let the connection establish — slow, but alive. In the planner:
   `via-hop` / `via-hop+front:` candidates get the largest FullDark bonus (+6) whenever
   the local Psiphon hop is alive. The reverse direction also exists: Psiphon's
   `upstreamProxyUrl` config can route Psiphon itself through the Rahyab hub (docs/06).
2. **shirokhorshid's aggressive server search was the best Psiphon finder.** That search
   lives in their fork of `psiphon-tunnel-core` — build the embedded AAR from
   `github.com/shirokhorshid/psiphon-tunnel-core` instead of vanilla (docs/06) and the
   hop inherits it.
3. **CDN fronting with clean/open IPs reached the open internet.** This is the
   `prefer_ips` mechanism: dial the clean IP, keep the CDN/allowed domain as SNI. In the
   planner, `ip<addr>` candidates; in the CDN-only environment they rank first.

Per-profile combination classes now auto-generated by the planner (bounded to 8 so the
racer stays fast, but every class the field data says matters):

| Variant | Meaning |
|---------|---------|
| `direct` | profile as-is |
| `ip<addr>` (×3) | TCP pinned to a clean/known-good IP, SNI keeps the domain |
| `front:<allowed-SNI>` (×2) | dial the server while claiming an allowed-domain SNI (`fonts.googleapis.com` / `www.gstatic.com` by default — both field-verified reachable) |
| `ip0+front:` | clean IP + allowed SNI |
| `via-hop` | chained through the local Psiphon SOCKS |
| `via-hop+front:` | Psiphon hop **and** allowed-SNI — the full-dark champion |

### The SNI-whitelisting recipe (your verified Tier-3, now expressible in Rahyab)

If the firewall whitelists by SNI (your data says it does for Fonts), a VLESS server can
ride through it by faking the SNI — the DPI sees the allowed domain, the connection goes
to your server. Express it in `rahyab.json`:

```json
{
  "link": "vless://UUID@YOUR-VPS-IP:443?security=tls#sni-escape",
  "sni": "fonts.googleapis.com",
  "insecure": true
}
```

**Open field question to test with `rahyab test`**: does the DPI also check that the
destination IP belongs to Google's ranges? Your data proves `GoogleSNI → GoogleIP` passes;
`GoogleSNI → yourVPS-IP` is the interesting unknown. Test it — if it passes, that's a
full-tunnel path through a whitelisting phase with zero cost.

## How this matrix gets FILLED with ground truth

`rahyab test --config rahyab.json` (the CLI combo-tester) does exactly this:
1. probes → prints the detected environment,
2. builds every candidate (all profiles × all variants: direct / IP-pinned / via-Psiphon),
3. health-checks each one individually and prints the live matrix (markdown table),
4. then races the top candidates concurrently like the app does,
5. saves `rahyab-matrix.json`.

Run it in every phase you experience, save the outputs — that turns this document
from educated guesses into your personal, evidence-based playbook.

## The planner's ranking rules (code: `algo.rs::env_fit`)

- `open`: everything allowed; 443 preferred; latency memory decides.
- `partial-tcp`: TLS-family (vless/trojan/ss) 8/10, plain proxies 3/10, non-443 ports penalized.
- `cdn-only`: `cdn_likely` (Workers/Pages/vercel domains, SNI-front, pinned-IP) 9/10, rest 1/10.
- `dns-only`: UDP-based (WireGuard) 7/10, TCP-based 1/10.
- `full-dark`: everything 1–2/10; keeps low-rate retries with exponential backoff (2s→5min)
  plus learned-memory bonuses (last-good +50, latency EMA, failure cooldowns).
